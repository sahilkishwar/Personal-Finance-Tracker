# Project File Documentation

This document explains the purpose of the important files in the Personal Finance Tracker project.

## 1. Project Overview

This project is a full-stack personal finance application with:

- A Java Spring Boot backend for API, persistence, and business logic
- An H2 in-memory database for local storage
- A React + Vite frontend for the UI

The app allows users to:

- add and view transactions
- filter by month and type
- set monthly budget limits
- view summaries and charts
- analyze income and expense trends

---

## 2. Root-Level Files

### .gitignore
Purpose:
- Tells Git which files and folders should not be committed.
- Usually excludes build outputs, environment files, editor settings, and dependency folders.

### .vscode/
Purpose:
- Stores editor-related configuration for the workspace.
- Helps keep code formatting and environment settings consistent.

### package-lock.json
Purpose:
- Lock file generated by npm.
- Ensures all frontend dependencies are installed consistently across machines.

### backend/
Purpose:
- Contains the Java Spring Boot backend application.

### frontend/
Purpose:

## 3. Backend Files

### backend/pom.xml
Purpose:
- Maven build configuration for the backend project.
- Declares project metadata, dependencies, parent Spring Boot version, and Java version.
- Controls packages such as Spring Web, JPA, and H2 database.

Key parts:
- `spring-boot-starter-parent` sets defaults for Spring Boot 3.5.0
- `java.version` tells Maven to build with Java 25
- Spring Boot starters provide most application features automatically

---

### backend/src/main/resources/application.properties
Purpose:
- Application configuration for Spring Boot.
- Sets the app name, port, and database settings.

Important settings:
- `server.port=8080` (or locally adjusted to avoid conflicts)
- `spring.datasource.url=jdbc:h2:mem:financedb` uses an in-memory H2 database
- `spring.h2.console.enabled=true` enables the H2 database console
- `spring.jpa.hibernate.ddl-auto=create-drop` recreates tables each startup

---

### backend/src/main/java/com/example/financetracker/FinancetrackerApplication.java
Purpose:
- Main entry point of the Spring Boot application.
- Starts the application when the backend is launched.

What it does:
- Calls `SpringApplication.run(...)` with this class.
- This is the starting point for the REST API server.

---

### backend/src/main/java/com/example/financetracker/config/DataSeeder.java
Purpose:
- Seeds sample budget data into the database on app startup.
- Helps the app have realistic starting values without manual inserts.

What it does:
- Checks whether transaction data exists
- Creates a few default budget entries like Food, Housing, Transport, etc.
- Saves them using the BudgetRepository

This is useful for demos and initial testing.

---

## 4. Backend Controllers

### backend/src/main/java/com/example/financetracker/controller/BudgetController.java
Purpose:
- REST controller for budget-related API endpoints.

Endpoints:
- `GET /api/budgets` – fetch budgets by month and year
- `POST /api/budgets` – create a budget
- `PUT /api/budgets/{id}` – update a budget
- `DELETE /api/budgets/{id}` – delete a budget

Important behavior:
- Uses `BudgetService` to perform logic
- Allows cross-origin requests from the frontend running on localhost:5174

---

### backend/src/main/java/com/example/financetracker/controller/TransactionController.java
Purpose:
- REST controller for transaction-related API operations.

Endpoints:
- `GET /api/transactions` – list all transactions
- `GET /api/transactions/{id}` – find one transaction by ID
- `GET /api/transactions/month` – list transactions for a specific month and year
- `GET /api/transactions/type/{type}` – filter by income or expense
- `GET /api/transactions/category/{category}` – filter by category
- `GET /api/transactions/summary` – fetch summary totals for a month
- `POST /api/transactions` – create a transaction
- `PUT /api/transactions/{id}` – update a transaction
- `DELETE /api/transactions/{id}` – delete a transaction

This is the main business API used by the frontend.

---

## 5. Backend Services

### backend/src/main/java/com/example/financetracker/service/BudgetService.java
Purpose:
- Business logic for budgets.
- Calls methods on `BudgetRepository`.

Responsibilities:
- get budgets by month and year
- save a new budget
- delete a budget
- find a matching budget category for a month

---

### backend/src/main/java/com/example/financetracker/service/TransactionService.java
Purpose:
- Business logic for transactions.
- Coordinates the transaction repository and returns processed data.

Responsibilities:
- get all transactions sorted by date
- find a transaction by ID
- get by month/year
- get by type
- get by category
- save and delete transactions
- calculate total income or expense for a month

---

## 6. Backend Repositories

### backend/src/main/java/com/example/financetracker/repository/BudgetRepository.java
Purpose:
- Data access layer for budgets.
- Extends `JpaRepository`, which gives built-in CRUD operations.

Custom query methods:
- `findByMonthAndYear(int month, int year)`
- `findByCategoryIgnoreCaseAndMonthAndYear(...)`

These let the service load budgets by category and date.

---

### backend/src/main/java/com/example/financetracker/repository/TransactionRepository.java
Purpose:
- Data access layer for transactions.
- Handles queries for listing and filtering transactions.

Custom methods:
- `findByTypeOrderByDateDesc(...)`
- `findAllByOrderByDateDesc()`
- `findByMonthAndYear(...)` using a JPQL query
- `findByTypeAndMonthAndYear(...)`
- `findByCategoryIgnoreCaseOrderByDateDesc(...)`

This is where most reporting queries live.

---

## 7. Backend Models

### backend/src/main/java/com/example/financetracker/model/TransactionType.java
Purpose:
- Enum for values used in financial transactions.

Values:
- `INCOME`
- `EXPENSE`

This is used to distinguish money entering the account from money leaving it.

---

### backend/src/main/java/com/example/financetracker/model/Transaction.java
Purpose:
- JPA entity representing a financial transaction.

Fields:
- `id` – primary key
- `title` – short description of the transaction
- `amount` – numeric amount
- `type` – `INCOME` or `EXPENSE`
- `category` – category such as Food, Housing, Salary, etc.
- `date` – transaction date
- `note` – optional notes

Annotations:
- `@Entity` marks it as a JPA entity
- `@Table(name = "transactions")` maps it to the transactions table
- `@Enumerated(EnumType.STRING)` stores enum names as strings

This is the central record for all transaction operations.

---

### backend/src/main/java/com/example/financetracker/model/Budget.java
Purpose:
- JPA entity representing a budget category for a specific month and year.

Fields:
- `id`
- `category`
- `limit` – monthly spending limit
- `month`
- `year`

Annotations:
- `@Entity` and `@Table(name = "budgets")`
- `@Column` names map Java fields to database column names like `budget_limit`

This model allows the app to compare actual spending with the allowed monthly limit.

---

## 8. Frontend Files

### frontend/package.json
Purpose:
- Defines the frontend package metadata and scripts.

Scripts:
- `npm run dev` starts the Vite development server
- `npm run build` creates a production build
- `npm run preview` serves the built app locally

Dependencies:
- React for UI rendering
- Recharts for charts and analytics visualization
- Vite for fast frontend development

---

### frontend/vite.config.js
Purpose:
- Vite configuration file.

Settings:
- `plugins: [react()]` enables React support
- `server.port: 5174` ensures the frontend runs on port 5174

---

### frontend/index.html
Purpose:
- Root HTML page used by the browser.
- Declares the page title and loads the app entry script.

Important part:
- `<div id="root"></div>` is the root DOM element where React mounts the app.

---

### frontend/src/main.jsx
Purpose:
- Bootstraps the React app.

What it does:
- Creates the React root
- Imports global styles from `index.css`
- Renders the `App` component inside the root container

---

### frontend/src/index.css
Purpose:
- Minimal reset CSS file.
- Resets margin and padding and ensures proper box sizing.

This is a small foundational style file that helps keep the app consistent across browsers.

---

### frontend/src/api.js
Purpose:
- Central API client for all frontend requests to the backend.

What it does:
- Sets the base URL for backend requests
- Has helper functions for `get`, `post`, `put`, and `delete`
- Exposes API methods such as:
  - `getTransactions()`
  - `getSummary()`
  - `createTransaction()`
  - `getBudgets()`
  - `createBudget()`

This file is the main communication layer between the UI and the backend server.

---

### frontend/src/App.jsx
Purpose:
- Top-level app component.
- Controls the active page and passes data into the current page view.

Behavior:
- Maintains `page` state such as dashboard, transactions, budgets, and analytics
- Calls `useFinance()` to load data from the backend
- Displays a global error message if the API is unavailable
- Renders the selected page component

---

### frontend/src/App.css
Purpose:
- Main styling file for the whole frontend.
- Contains all layout, component, card, form, chart, and navbar styling.

Topics covered:
- theme colors and variables
- cards and widgets
- summary cards
- transactions list
- forms
- analytics charts
- responsive design

This is the primary stylesheet for the application.

---

### frontend/src/hooks/useFinance.js
Purpose:
- Custom React hook that loads finance data from the backend.

Responsibilities:
- tracks current `month` and `year`
- stores transactions, budgets, and summary
- fetches data via `api.getTransactionsByMonth`, `api.getBudgets`, and `api.getSummary`
- handles loading and error states
- exposes `refresh` to reload data after create/delete actions

This is the main data layer for the UI.

## 12. Summary

The project is structured as a clean separation of responsibilities:

- Backend handles persistence, API routes, and business logic
- Frontend handles user interaction, display, and charts
- Shared constants and API helper files keep the project organized
- The app uses a simple in-memory H2 database for local development

This architecture is easy to extend if you later add:

- authentication
- user accounts
- export to CSV
- recurring transactions
- recurring budgets
- more detailed reports
